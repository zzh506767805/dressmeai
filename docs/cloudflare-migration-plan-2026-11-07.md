# Cloudflare 免费额度迁移计划

日期：2026-11-07。状态：仅规划，未修改业务代码、未部署、未更改域名或服务配置。

## 建议与边界

目标组合为 Cloudflare Workers（网站与接口）+ R2 Standard（图片）+ D1（业务数据）。阿里云试衣和 Stripe 保留。免费指托管、存储和数据库在免费额度内，AI 调用、支付手续费、域名续费仍有成本。现阶段不能保证现有 Next.js 整站在 Workers Free 稳定运行，先完成兼容性与资源用量验证，再决定正式迁移。

飞书多维表可以存附件，但获取的素材下载链接只有 24 小时有效期，获取链接需要应用权限，部分多维表还需要额外授权参数。不能把临时链接作为长期图片地址存入历史。若以飞书为存储源，必须保存 file_token，由后端动态获取下载链接或代理文件，并验证阿里云实际抓图、链接刷新、限流与海外访问。这增加依赖与维护，不作为生产图床首选；可选用于运营记录，记录 R2 图片链接，无需复制客户照片。

## 已核实的项目现状

- Next.js 14.1.0，Pages Router，多语言路由与静态页面；当前构建输出 standalone。
- PostgreSQL + Prisma 6.19.2，包含用户、登录账户、会话、支付、试衣任务、保存的人物照。
- `lib/blob.ts` 集中处理 Azure 图片上传与删除；`pages/api/upload.ts` 使用 sharp 压缩、旋转图片。
- `pages/api/status.ts` 使用 sharp 制作历史免费用户的水印结果，并持久化 AI 原图；`lib/payments.ts` 有根据 Azure 域名判断原图是否已持久化的逻辑，迁移时必须同步调整。
- `lib/credits.ts` 使用交互式事务退回次数，不能直接更换数据库地址后认为 D1 已完成迁移。
- 扣次数与创建任务、记录付款与发放权益目前存在分步写入；数据库迁移要验证中途失败与重复请求，确保不会扣次数但没有任务、收款但没有权益。
- 已有设计依赖跨登录/支付恢复两张图，以及数据库生成历史；必须保留这些行为。

## 免费额度与上线门槛

以下为本次查阅官方文档得到的额度，执行时再次核实账户页面：

| 服务 | 免费额度 | 对项目的影响 |
| --- | --- | --- |
| Workers Free | 每天 10 万次动态请求；每次 10ms CPU | 网络等待不计 CPU，但登录、页面渲染、签名和大体积 JSON 处理可能超限；需真实预发布测量 |
| Workers 静态资源 | 直接由静态资源服务响应的请求免费且不限次数 | 优先利用现有静态页面；经过 Worker 的请求仍按动态请求计算 |
| R2 Standard | 每月 10 GB-month 存储；100 万次 A 类操作、1000 万次 B 类操作；公网出站流量免费 | 属于按量计费服务中的免费额度，启用通常需要支付方式，超额会产生费用；不是自动封顶的免费图床 |
| D1 Free | 每天读取 500 万行、写入 10 万行；账户总存储 5GB，单库上限 500MB | 图片存 R2；单库容量与索引实际读写量需要监控 |

当前未核实生产数据库容量、图片总量、实际动态请求量，不能据此承诺零账单。上线前盘点这些数据。输入临时图可以设置合理清理周期；付费结果与保存的人物照不能为了省空间自动删除而破坏用户已有权益。计费提醒不等于硬性支出上限。

## 执行顺序与验收

1. **免费方案预验证，预计 0.5—1 天。** 使用独立预发布环境验证现有 Pages Router、多语言、Google 登录、Stripe 签名、数据库访问和图片上传。检查打包体积与实际 CPU 使用。官方目前提供 vinext（beta）及 OpenNext 路径，按本项目兼容性选择，不默认为迁移重写页面。Next.js 版本按选定部署工具要求更新。若免费上限不满足，先给出实测结果，再选择约 5 美元/月起的 Workers Paid 或调整方案；不承诺免费稳定性。
2. **图片迁移，预计 1—2 天。** 将 Azure 存储实现替换为 R2；浏览器先压缩、修正手机照片方向，再上传二进制，减少大 base64 的处理与跨登录存储超限。服务端验证登录、文件大小、格式和归属，避免开放上传耗尽额度。AI 输入使用可供阿里云抓取的短期授权地址；私人人物照和结果保存在私有桶，下载经过身份校验。成功原图直接流式写入 R2，保留历史水印原图与解锁能力，单独验证旧水印生成的替代实现，不用浏览器遮罩冒充受保护结果。不把付费 Cloudflare Images 当成免费前提。
3. **数据库迁移，预计 1—2 天。** 为 D1 建立兼容表结构与索引，评估 Prisma D1 适配器，避免无必要更换全部数据访问代码。把现有交互式事务调整为 D1 支持的原子条件更新/事务批处理；付款入账、权益发放、扣次数与创建任务、失败退回均须验证并发和重试。备份后导入用户 ID、Google 账户关联、支付与订阅记录、剩余次数、试衣历史和图片映射。若 D1 兼容成本过高，阶段性保留 PostgreSQL；此时明确仍有数据库费用，不能称为完全免费迁移。
4. **流程验收，预计 0.5—1 天。** 用测试付款覆盖单次购买、订阅、续费、取消、重复支付通知；覆盖登录与付款后恢复图片、生成失败只退一次、关闭网页后结果仍能取回、历史原图解锁和下载。保留异步提交与轮询，补充必要的定时恢复，确保网页关闭后任务也能完成持久化；只有 R2 保存成功才确认结果长期可取，存储失败保持可重试。定时任务也须符合 Free 限制。复核现有支付审查文档中通知配置的遗留问题，按实际线上状态处理。
5. **切换与撤旧，预计 0.5 天加观察期。** 在正式切换前备份数据库与图片；复制图片并校验数据库中全部相关 URL，包括原图、结果图和保存的人物照。短暂暂停写入，处理进行中的试衣任务与 Stripe 到达事件，完成增量数据同步后再开放，避免两个站点各自写库。配置 Google 回调、Stripe 通知、密钥与域名；保留原 Azure 服务及快照观察 3—7 天。回滚先暂停写入，协调支付通知，回补新站新增数据，不能只切回域名丢失新订单。验证通过后再停 Azure，并更新项目文档与部署说明。

预计总投入约 4—7 个工作日，另有观察期；这是计划估计，实际取决于兼容验证、数据规模和历史水印逻辑。
